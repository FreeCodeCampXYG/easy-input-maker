# 输入与音乐链路审计（2026-09-06）

## 范围与证据

本轮检查第一槽默认按键/PTT 路由、钢琴合成、鼓机时钟、曲目播放和扬声器 worker，并复核共享的配置接收/NVS、按键状态/传输绑定、音频仲裁、睡眠策略和构建依赖入口。不是所有第三方源码的逐行审计、整个仓库的泄漏认证或实板功耗测试。

当前分支为 `my-host-action-practice`。README 中课程起点、57 项测试和旋钮短按切槽的历史说明不能代表当前实践分支；当前手势与功能以源码和 DEV_STATE 为准。

## T3 误输入：尚未定位根因

- 默认 KEY3 是 EditPttHold，使用配置中的 edit_ptt_hotkey；Windows 平台默认值为 Ctrl+Shift+E。保存的 NVS 可以覆盖默认值。
- 可解析的 PTT 快捷键进入 HeldKeyboard/HID，不能仅凭 bridge 标志认为其只发给 companion。默认 KEY3 的路径未直接调用 Paste/FixedText。
- 尚未读取设备实际映射、复现应用焦点行为或检查 companion 的复制/粘贴实现，不能断言为 Codex、固件或电脑端某一方缺陷。
- 最小定位信息：是否第一槽第 3 个实体键；实际快捷键与目标平台；按下瞬间或松开后发生；输出是旧剪贴板内容、识别结果还是字母。仅用无敏感内容的测试文本复现。
- 对比同一焦点下手动按相同快捷键与实体键，再在普通编辑器复现；同步确认 companion 版本与绑定。若手动快捷键也复现，应继续检查主机快捷键拦截和文本替换链路。

## 性能与资源建议

1. **暂停功耗优先测量**：曲目 playing / 鼓机 session_active 在暂停时仍为真，worker 继续渲染和写 PCM，因而保留 I2S/扬声器所有权。修复持续音不等于关闭硬件。后续可设计“保留曲目状态、排空 I2S、等待通知、恢复资源”路径，必须与麦克风优先级和 GPIO8 共享消费者一起验证，不能直接拉低共享电源。
2. **减少热循环重复计算（第二轮已实施）**：包络步长改为 apply_config 时缓存，构造也复用同一配置入口。8 组优化前 PCM 指纹与优化后完全一致，覆盖四种音色、八键复音、运行中改配置和释放尾音。增加两个 uint32 缓存字段；未声称 ESP32 实测提速或节电比例。
3. **改善音频帧内时序**：当前 worker 以 10 ms 分帧，曲目先 advance 再 render；鼓机接口只返回本次最后命中的鼓声。长期偏拍修复仍不代表采样级准确。后续可按事件边界分段渲染，测试短音符、休止、跨帧边界与 300 BPM 的 PCM 起音位置。
4. **长时内存验证**：音乐核心使用定长数组，没有每音符堆分配；麦克风池有任务、队列、信号量和 heap_caps 对应释放，初始化失败有锁存保护。仍需实板反复切槽、录音抢占、播放暂停、连接断开，记录最小空闲堆、最大连续块、任务栈余量和恢复空闲后的趋势，才能判断泄漏或碎片化。
5. **结构去重（第二轮已实施）**：扬声器七类命令统一经私有 enqueue_music_command 入队，保持 16 项容量、临界区、FIFO 和失败返回。Note 的最终位图/满队列 release 补偿保留。原版资产播放、麦克风与睡眠链仍有调用者，不作为“冗余模块”删除。
